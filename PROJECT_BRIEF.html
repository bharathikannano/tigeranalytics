📤 Upload Flow
1User drops or selects CSV → Axios POSTs multipart/form-data with onUploadProgress → progress bar updates live
2Express: multer checks MIME type + file size → PapaParse parses buffer → 5 required columns validated
3Every row validated via validateCsvRow() → if any fail, 422 with full error list returned to UI
4All rows valid → single SQLite transaction: INSERT upload_log + all N pricing_records atomically
5201 success → TanStack Query invalidates ['upload-logs'] cache → history auto-refreshes
🔌 REST API Endpoints

GET/api/pricing/upload-logsPaginated upload audit history

Design Decisions
Key architectural choices and the rationale behind them
#DecisionWhy
D1SQLite + better-sqlite3Zero infrastructure. Synchronous API simplifies Express handlers. WAL enables concurrent reads.
D2All-or-nothing CSV validationEvery row validated before any write. No partial state. Users get a full error list to fix before re-uploading.
D3In-memory CSV parsingmulter memoryStorage + PapaParse from Buffer. No temp files. Header normalisation makes format forgiving.
D4Atomic bulk insert transactionupload_log + all pricing_records in one transaction. Any failure rolls everything back. Audit log stays in sync.
D5ORDER BY allowlistsortBy / sortDir validated against hardcoded arrays before SQL interpolation — prevents ORDER BY injection.
D6Axios HTTP clientClean instance config, interceptors for error standardisation, automatic serialisation, and native onUploadProgress.
D7Vite /api proxyProxies /api to port 4000 in dev. Eliminates CORS issues. Production uses VITE_API_URL env var.
D85 covering indexesOn store_id, sku, record_date, (store_id,sku), product_name — matching the most common filter patterns.
D9COALESCE partial UPDATEPUT endpoint only needs changed fields. Inline editor sends only modified fields, reducing payload and risk.
D10Centralised error handlerOne middleware handles multer, validation, and 500 errors uniformly. Stack traces suppressed in production.
D11TanStack QueryReplaces manual loading/error state boilerplate. 30s cache, auto-refetch on mutation, optimistic cache patches.
D12filters vs activeFilters splitFilterBar updates filters (local). Search click copies to activeFilters (query key). No network call on each keystroke.
D13Dynamic CORS for localhostIn dev, any http://localhost:* port is allowed. Fixes port conflicts when Vite auto-increments port numbers.
D14Cell component in PricingTableReusable <Cell> component halves the JSX needed for each editable column.
D15AWS Amplify static hostingFrontend deployed to Amplify CDN. amplify.yml points appRoot to /client. architecture.html placed in /public.

Assumptions
Design constraints and accepted trade-offs
  • 🔐
    Internal users only — no auth layerTrusted retail operations staff. Adding OAuth/JWT would be the first production hardening step.
  • 📄
    CSV format contractFeeds always contain the five required columns. Header matching is case-insensitive and whitespace-tolerant.
  • 📦
    Reasonable file sizesUploads expected to stay under 50 MB per file, configurable via UPLOAD_SIZE_LIMIT_MB.
  • 🖥️
    Single-server deploymentSQLite suits one process. Horizontal scaling requires migrating to PostgreSQL.
  • ➕
    Append-only ingestionUploads always insert new rows. Duplicates permitted; de-duplication can be added if required.
  • 📅
    Date format flexibilityAny date parseable by new Date() is accepted and normalised to YYYY-MM-DD in storage.
  • 🚀
    Node.js v18+ runtimeA process manager (pm2 / systemd) is expected in production for restarts and log rotation.

# API call
curl -s "http://localhost:4000/api/pricing?storeId=STORE-001&sku=ABC-001"

-- Underlying SQL (parameterised prepared statement)
SELECT * FROM pricing_records
WHERE  store_id LIKE @storeId AND sku LIKE @sku
ORDER BY created_at DESC
LIMIT 50 OFFSET 0;
